47. [TOOL] Never detect Vercel deployment status by parsing `vercel ls` output — the CLI writes the human status table (the `● Ready` column) to STDERR while stdout gets bare deployment URLs, so the ubiquitous `2>/dev/null | grep Ready` watcher matches nothing and hangs forever (this silently broke deploy-watching in session after session; proven and fixed 2026-07-19, CAR-168). 48. [TOOL] Never trust a local `eslint`/`tsc` run to predict CI when type-aware linting is on — CI runs Lint and `tsc --noEmit` BEFORE Build, so `.next/` does not exist there, while a local checkout almost always has one left by a previous build. `tsconfig.json` includes `.next/types/**/*.ts`, and those generated route types transitively pull files into the TypeScript program that the `include` globs never matched, so a file can be typechecked locally and absent from the program in CI. With `parserOptions.projectService` enabled, absent-from-program is a hard `Parsing error: … was not found by the project service`, not a silent skip. The specific trap: TypeScript's `**` glob does NOT match directories whose name starts with a dot, so `"**/*.ts"` never covered `src/app/.well-known/**` — those two routes had never been typechecked in CI at all, and CAR-158's typed-lint block turned that latent gap into a red build (2026-07-20). Verify any lint/tsconfig change by moving `.next` aside and re-running both commands cold; a dot-directory under `src/` must be named explicitly in `include`.
    > **Localized** — the guard lives at `careervine/tsconfig.json:42-49`: `src/app/.well-known/**/*.ts` is named explicitly in `include`, with a comment explaining that `**/*.ts` does not match dot-directories and that `.next/types` masked the gap locally.
